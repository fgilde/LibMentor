# Release setup

## One-time setup

The public [fgilde/LibMentor](https://github.com/fgilde/LibMentor) repository is available. Enable GitHub Pages with GitHub Actions as its source:

```powershell
gh api --method POST repos/fgilde/LibMentor/pages -f build_type=workflow
```

If Pages is already configured, use the repository's Settings > Pages page to select GitHub Actions instead of creating a second site.

In the `fgilde` NuGet account, create a Trusted Publishing policy:

| Field | Value |
| --- | --- |
| Repository owner | `fgilde` |
| Repository | `LibMentor` |
| Workflow file | `release.yml` |
| Package scope | `LibMentor` |
| Environment | Leave empty |

Allow the first package publication as well as new versions. Confirm that the package ID is available before the first push; an absent GitHub repository does not reserve a NuGet ID.

## Release

1. Change the version in `Directory.Build.props` and `libmentor.json`.
2. Run the CI checks locally or through a pull request.
3. Merge the version change into `main`. Changes to `Directory.Build.props` automatically start the Release workflow. Updates to the release workflow itself also run the publication checks.

Matching `v<version>` tags remain supported: `v0.1.0` publishes package `LibMentor` version `0.1.0`. All release runs are serialized, and existing NuGet versions are skipped rather than replaced.

For the first release, the same workflow can also be started from Actions > Release > Run workflow, with `version` set to `0.1.0`, or remotely:

```powershell
gh workflow run release.yml --repo fgilde/LibMentor --ref main --field version=0.1.0
```

Configure the NuGet Trusted Publishing policy before starting the release. Manual runs validate the requested version against the project version.

The release workflow validates tag or manual versions when provided, allows automatic publication only from main, runs tests, packs and installs the actual package, exercises the CLI, then exchanges OIDC credentials and publishes. Do not tag again to replace a package; NuGet versions are immutable.

A successful push means NuGet accepted the package upload. NuGet validates and indexes new packages before they become publicly restorable. If an exact-version restore reports that the new version is missing, check its validation/indexing status in the owner's Manage packages view. See [NuGet package validation and indexing](https://learn.microsoft.com/en-us/nuget/nuget-org/publish-a-package#package-validation-and-indexing).

The normal CI workflow tests Windows and Linux, checks formatting, packs and smoke-tests the actual tool. Documentation deployment uses the CLI from the same source checkout.

## Optional Context7 registration

After the documentation URL is public, use Context7's authenticated API to add its `llms.txt` URL. The optional workflow is manually dispatched and requires repository secret `CONTEXT7_API_KEY`. It does not run for pull requests. Ownership claiming uses the public key generated by Context7's own claiming UI; never invent a key or overwrite an existing `context7.json`.
