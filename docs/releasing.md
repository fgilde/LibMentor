# Release setup

## One-time setup

Enable GitHub Pages with GitHub Actions as the source for the documentation website:

```powershell
gh api --method POST repos/fgilde/LibMentor/pages -f build_type=workflow
```

If Pages is already configured, use the repository's Settings > Pages page to select GitHub Actions instead of creating a second site.

In the `fgilde` NuGet account, create a Trusted Publishing policy:

| Field | Value |
| --- | --- |
| Repository owner | `fgilde` |
| Repository | `LibMentor` |
| Workflow file | `release.yml` |
| Package scope | `LibMentor` |
| Environment | Leave empty |

The policy is already used for publication. Keep its repository, workflow and environment values aligned with release.yml.

## Release

1. Change the version in `Directory.Build.props` and `libmentor.json`.
2. Run the CI checks locally or through a pull request.
3. Merge the version change into `main`. Changes to `Directory.Build.props` automatically start the Release workflow. Updates to the release workflow itself also run the publication checks.

Matching `v<version>` tags remain supported: `v0.1.1` publishes package `LibMentor` version `0.1.1`. All release runs are serialized, and existing NuGet versions are skipped rather than replaced.

The workflow can also be started from Actions > Release > Run workflow with the current project version, or remotely:

```powershell
gh workflow run release.yml --repo fgilde/LibMentor --ref main --field version=0.1.1
```

Configure the NuGet Trusted Publishing policy before starting the release. Manual runs validate the requested version against the project version.

The release workflow validates tag or manual versions when provided, allows automatic publication only from main, runs tests, packs and installs the actual package, exercises the CLI, then exchanges OIDC credentials and publishes. Do not tag again to replace a package; NuGet versions are immutable.

A successful push means NuGet accepted the package upload. NuGet validates and indexes new packages before they become publicly restorable. If an exact-version restore reports that the new version is missing, check its validation/indexing status in the owner's Manage packages view. See [NuGet package validation and indexing](https://learn.microsoft.com/en-us/nuget/nuget-org/publish-a-package#package-validation-and-indexing).

The final release step waits for public feed availability, then installs the exact package from an isolated nuget.org-only configuration and runs init, generation and drift checks. It allows up to 30 minutes for validation/indexing and fails explicitly if the package is still unavailable. The local package smoke test and the public-distribution test are separate checks.

The normal CI workflow tests Windows and Linux, checks formatting, packs and smoke-tests the actual tool. It then generates LibMentor's own documentation, verifies output drift and assembles the website.

## Documentation website

The buildless website is maintained in website/. The documentation workflow runs LibMentor from the same source checkout, then scripts/build-site.ps1 copies the website, package icon and generated documentation into artifacts/site. The generated context is published under ai/; the landing page is at the site root. No consumer repositories are checked out or copied into this site.

The version shown on the landing page comes from the generated knowledge model and is checked against Directory.Build.props. PackageProjectUrl remains https://libmentor.gilde.org/ and RepositoryUrl remains https://github.com/fgilde/LibMentor. The package icon is embedded from assets/icon.png.

## Optional Context7 registration

After https://fgilde.github.io/LibMentor/ai/llms.txt is public, use Context7's authenticated API to add that URL. The optional workflow is manually dispatched and requires repository secret `CONTEXT7_API_KEY`. It does not run for pull requests. Ownership claiming uses the public key generated by Context7's own claiming UI; never invent a key or overwrite an existing `context7.json`.
